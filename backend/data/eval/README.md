# Оценка качества

`make eval` или `cd backend && uv run python -m app.cli eval` читает текущие знания из БД,
печатает таблицу и сохраняет JSON в `quality_reports`. Оператор получает последний отчёт через
`GET /api/v1/console/quality`; до первого прогона API возвращает 404.

Обычный прогон не создаёт LLM-адаптер и не обращается к LLM даже при настроенном ключе.
`python -m app.cli eval --llm` дополнительно оценивает **только намерения** через существующий
LLM-разборщик. Нужны настроенная модель и `LLM_MODE=auto`; ответы запасных правил исключаются
из метрик LLM и учитываются отдельным счётчиком. Этот путь в приведённом прогоне не запускался.
Сравнение LLM для Связного/Куратора и стоимости моделей остаётся отдельной задачей B3.3.

## Как устроены наборы

- `intents.yaml` (R2): известные ключи чипов сравниваются как множества, без label/важности.
  Неизвестные пожелания учитываются отдельно по количеству. Для поездки сравниваются все
  размеченные поля; дата разбора зафиксирована на 28.10.2026, чтобы результат не зависел от дня запуска.
  В JSON сохранены TP/FP/FN и precision/recall/F1 для каждого ключа, точность каждого поля поездки,
  а также число правильно разобранных непустых полей.
- `hotelier_answers.yaml` (R3): используется оценщик Связного. Поля `conditions`, `window_type`,
  `notes` содержат свободные формулировки и исключены из exact-match; их список виден в отчёте.
  Низкая ясность оценивается по необходимости переспроса.
- `curator.yaml` (R8): `propose` сравнивается с ожидаемым методом и ключевыми параметрами.
  `cannot` нормализуется в `cannot_check`, радиусы и теги — в общий формат.
  Свободные тексты `question`/`reason` исключены, схемы ответов включены.
- `search_queries.yaml`: **оценки команды по фактам расчёта**, автоматически выставленные
  по явной рубрике, без фотографий. Это регрессионная проверка согласованности поиска с моделью;
  независимой оценкой качества отелей она не является. 20 исходных текстов взяты из R2.
  По 12 отелей в фиксированном пуле на запрос, 16 запросов различают релевантность кандидатов,
  у 4 все кандидаты имеют одинаковую оценку. nDCG считается внутри этого пула с бюджетом/гостями
  из разбора. Полный поиск по всем 200 отелям этой цифрой не оценивается.
  Метки не обновляются во время `eval`; `evidence` хранит значения, области и ID исходных фактов.
  Для явного пересоздания: `cd backend && uv run python -m pipeline.quality_search`.
- `gold.yaml`: заготовка независимой ручной разметки с OSM ID, характеристикой, фасадом, этажом,
  месяцем, меткой да/нет, автором и открытыми источниками. Сейчас `labels: []`.

Без gold значения `accuracy`/`ece` равны `null`, `n=0`. При появлении меток расчёт сопоставляет их
только с единственным актуальным булевым фактом соответствующей области. Пропуски и неоднозначные
совпадения отражаются в `gold.unmatched`. Вероятность отрицательного утверждения переводится в
P(да) как `1-confidence`. ECE — взвешенное среднее расхождения P(да) и частоты меток «да» в
10 равных бинах. `perCharacteristic[].reliability` содержит точки диаграммы надёжности:
`from`, `to`, `n`, `meanProbability`, `positiveRate`; у пустого бина средние равны `null`.
