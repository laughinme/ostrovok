# Оценка качества

`make eval` или `cd backend && uv run python -m app.cli eval` читает текущие знания из БД,
печатает таблицу и сохраняет JSON в `quality_reports`. Оператор получает последний отчёт через
`GET /api/v1/console/quality`; до первого прогона API возвращает 404.

Обычный прогон не создаёт LLM-адаптер и не обращается к LLM даже при настроенном ключе.
`python -m app.cli eval --llm` дополнительно оценивает **только намерения** через существующий
LLM-разборщик. Нужны настроенная модель и `LLM_MODE=auto`; ответы запасных правил исключаются
из метрик LLM и учитываются отдельным счётчиком. Этот путь в приведённом прогоне не запускался.
Сравнение LLM для Связного/Куратора и стоимости моделей остаётся отдельной задачей B3.3.

## Как устроены наборы

- `intents.yaml` (R2): известные ключи чипов сравниваются как множества, без label/важности.
  Неизвестные пожелания учитываются отдельно по количеству. Для поездки сравниваются все
  размеченные поля; дата разбора зафиксирована на 28.10.2026, чтобы результат не зависел от дня запуска.
  В JSON сохранены TP/FP/FN и precision/recall/F1 для каждого ключа, точность каждого поля поездки,
  а также число правильно разобранных непустых полей.
- `hotelier_answers.yaml` (R3): используется оценщик Связного. Поля `conditions`, `window_type`,
  `notes` содержат свободные формулировки и исключены из exact-match; их список виден в отчёте.
  Низкая ясность оценивается по необходимости переспроса.
- `curator.yaml` (R8): `propose` сравнивается с ожидаемым методом и ключевыми параметрами.
  `cannot` нормализуется в `cannot_check`, радиусы и теги — в общий формат.
  Свободные тексты `question`/`reason` исключены, схемы ответов включены.
- `search_queries.yaml`: **оценки команды по фактам расчёта**, автоматически выставленные
  по явной рубрике, без фотографий. Это регрессионная проверка согласованности поиска с моделью;
  независимой оценкой качества отелей она не является. 20 исходных текстов взяты из R2.
  По 12 отелей в фиксированном пуле на запрос, 16 запросов различают релевантность кандидатов,
  у 4 все кандидаты имеют одинаковую оценку. nDCG считается внутри этого пула с бюджетом/гостями
  из разбора. Полный поиск по всем 200 отелям этой цифрой не оценивается.
  Метки не обновляются во время `eval`; `evidence` хранит значения, области и ID исходных фактов.
  Для явного пересоздания: `cd backend && uv run python -m pipeline.quality_search`.
- `gold.yaml`: заготовка независимой ручной разметки с OSM ID, характеристикой, фасадом, этажом,
  месяцем, меткой да/нет, автором и открытыми источниками. Сейчас `labels: []`.

Без gold значения `accuracy`/`ece` равны `null`, `n=0`. При появлении меток расчёт сопоставляет их
только с единственным актуальным булевым фактом соответствующей области. Пропуски и неоднозначные
совпадения отражаются в `gold.unmatched`. Вероятность отрицательного утверждения переводится в
P(да) как `1-confidence`. ECE — взвешенное среднее расхождения P(да) и частоты меток «да» в
10 равных бинах. `perCharacteristic[].reliability` содержит точки диаграммы надёжности:
`from`, `to`, `n`, `meanProbability`, `positiveRate`; у пустого бина средние равны `null`.


## Заявления отелей на официальных сайтах (R7, 28.10)

`official_claims.yaml` — что 40 отелей каталога пишут о себе (собрано ChatGPT по официальным страницам,
пересказ с URL; у 14 сайт не найден или недоступен). Фасады и этажи сайты почти не называют, поэтому
сверка на уровне отеля, раздел `officialClaims` отчёта:

| Проверка | Результат |
|---|---:|
| Отель заявляет вид на море/горы → у нас есть окно с P(да) ≥ 0,5 | 12/14 |
| Минуты до пляжа против нашего пешего маршрута (±5 мин или ±50 %) | 5/7 |
| Метры до моря против расстояния по прямой до ближайшего пляжа OSM (±150 м или 0,5–2×) | 2/8 |

Оба промаха по видам — привязка, а не расчёт: точка OSM «Спутника» стоит на одноэтажном корпусе,
вид на горы у «Мыс Видный» заявлен для корпуса «Арена» по другому адресу. Метры сайты занижают:
ближайший пляж на карте в медиане в 2,3 раза дальше («100 м» у МИРИТ — 381 м по прямой). Отрицательных
меток по видам нет, поэтому это проверка полноты, а не калибровка; `gold.yaml` по-прежнему пуст.

## Сравнение моделей и Vertex Gemini (28.10)

`make eval-compare` печатает сохранённые результаты. `[архив v1]` — исходные прогоны до исправления
метрик: для ответов отеля и Куратора в них ещё могли учитываться откаты на правила. Новые отчёты
(`evaluationVersion: 2`) исключают откаты во всех трёх задачах и показывают число ответов LLM.
F1 намерений проверяет ключи желаний, а не точность всех параметров, отрицаний и важности.
Отложенный набор синтетический; он не доказывает точность реальных видов и маршрутов.

Пример нового прогона Vertex AI с существующим ключом в локальном `.env` (расходует кредиты):

```sh
cd backend
uv run python -m app.cli eval --llm \
  --model google/gemini-3.5-flash-lite --strong-model google/gemini-3.5-flash-lite \
  --thinking low --thinking-strong medium \
  --base-url https://aiplatform.googleapis.com/v1/projects/PROJECT_ID/locations/global/endpoints/openapi \
  --key-env GEMINI_VERTEX_API_KEY
```

Замените `PROJECT_ID` своим проектом. Адаптер использует `x-goog-api-key`; ключи в отчёты не записываются.
`--key-env` читает переменную процесса или root/backend `.env`, переменная процесса приоритетна.
`--cached-only` вместе с `--llm` пересчитывает метрики только по кэшу без запросов к модели.
Кэш сохраняет исходную задержку и оценку цены; текущий расход кэшированного ответа равен нулю.
`history/` хранит live-прогоны перед повторным подсчётом; корневые JSON — последний подсчёт.

Цена ориентировочная: успешные запросы учитываются по токенам, таймауты могут оплачиваться провайдером,
даже если наш процесс не получил usage. Нулевой `costUsd` при `cacheOnly` не означает бесплатную модель.
Квота/429 и таймауты отражаются отсутствием ответа LLM; высокую точность на малой отвеченной доле
нельзя сравнивать с полной выборкой без этого ограничения. Текущий таймаут обычных задач — 15 с,
Куратора — 30 с, общий лимит Куратора — 8 запросов и 8 вызовов инструментов.

`llm-examples.json` — реальные запросы/ответы/инструменты из оценочных данных.
`live-intents.json` — HTTP-проверка режима правил и повторных ответов LLM из кэша.

## Polza.ai, ключ жюри (29.10)

Проверен `openai/gpt-5.6-luna`, low/medium, через `https://polza.ai/api/v1`.
Текущий Chat Completions поддерживает reasoning вместе с инструментами без правок адаптера.
Повторный прогон расходует баланс, кэш используется автоматически:

```sh
make eval-llm LLM_MODELS=openai/gpt-5.6-luna \
  LLM_EVAL_ARGS='--thinking low --thinking-strong medium --base-url https://polza.ai/api/v1 --key-env POLZA_API_KEY'
```

`POLZA_API_KEY` задаётся только в локальном `.env`. Получено 179/179 ответов без откатов:
hold-out — намерения F1 1,00 (40/40), поля ответов 0,94 (30/30), метод Куратора 0,93 (15/15).
Медиана / p95 разбора — 2,82 / 4,73 с.
[Полный JSON](llm/openai_gpt-5.6-luna.low+openai_gpt-5.6-luna.medium.5086a6e110.json)
и [короткие проверки](polza-smoke.json) сохранены: цепочка инструментов, structured output,
HTTP с ключом жюри, сохранение дат при чтении кэша, отказ 402 при недостаточном лимите ключа.
Все проверки вместе стоили 8,65 ₽ по биллингу Polza; USD в JSON — отдельная оценка по тарифам модели.

У ключа жюри лимит 100 ₽ за всё время. API проверен с этой машины, внешний адрес — FR;
доступ именно из РФ без VPN заявлен [сервисом](https://polza.ai/alternatives),
но этой сессией не проверен. Один прогон не измеряет долговременную доступность.
