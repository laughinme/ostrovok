# Спайк горизонта B1.0

Самостоятельный эксперимент, не импортируется из `app` и не меняет зависимости рантайма.

```sh
uv run backend/pipeline/spikes/horizon_spike.py
# Сравнение дискретизации рельефа (по умолчанию 30 м):
uv run backend/pipeline/spikes/horizon_spike.py --step 60
# Необязательный слой ж/д для карты:
uv run backend/pipeline/spikes/horizon_spike.py --hotel morskaya_zvezda --railways
# Один отель:
uv run backend/pipeline/spikes/horizon_spike.py --hotel zhemchuzhina
```

Зависимости объявлены в PEP 723 заголовке скрипта. Также работает явный запуск:

```sh
uv run --no-project --with numpy --with shapely --with httpx --with rasterio \
  --with matplotlib --with pyproj python backend/pipeline/spikes/horizon_spike.py
```

Все исходные ответы, GeoTIFF, маски моря, сцены NPZ, отчёты JSON и изображения сохраняются
в `backend/.cache/spike/`, исключённой правилом `.cache`. Файлы `*.source.json` содержат URL,
запрос и дату загрузки; ответы Overpass - дату снимка OSM. При наличии кэша сеть не используется.
Повторная загрузка: удалить конкретный исходный файл и производные `*_sea.geojson`, если меняется берег.
После изменения координат отеля нужно удалить и его выгрузку зданий/железной дороги.

Выгрузка OSM: зеркало Mail.ru, `User-Agent: okno-hackathon/0.1`; до шести попыток с увеличивающейся паузой при временных ошибках. Здания запрашиваются по охватывающему прямоугольнику и отбираются
по точному расстоянию до точки отеля ≤ 2 км в локальной AEQD проекции. Полные контуры сохраняются.
Члены мультиполигонов не дублируются отдельными зданиями, внутренние дворы учитываются.

Три отеля выбраны из OSM, координаты и этажность читаются заново из их контуров:

| Ключ | Здание OSM | Сценарий |
|---|---|---|
| `zhemchuzhina` | way/51847429 | Центр Сочи, первая линия, 17 этажей |
| `morskaya_zvezda` | way/53549358 | Хоста, в глубине застройки, 12 этажей |
| `marriott_polyana` | way/227214566 | Эстосадок, 8 этажей |

## Расчёт и артефакты

- `horizon_data.py`: HTTP, кэш, OSM-контуры, береговая линия, тайлы Copernicus.
- `horizon_geometry.py`: геометрия фасадов/лучей и чистое NumPy-ядро `evaluate_horizon`.
- `horizon_plot.py`: диагностические панорамы и карты.
- `horizon_spike.py`: подготовка сцен, замеры, отчёт.
- `test_horizon_spike.py`: искусственные сцены без сети.

Слой ж/д из кэша читается автоматически; `--railways` включает его загрузку из Overpass.
Он нужен для диагностики карты и не участвует в расчёте горизонта.

Для каждого отеля: `{key}_sea.png`, `{key}_inland.png` (по три этажа на изображение),
`{key}_context.png` (карта зданий и ж/д), `{key}_{facade}_scene.npz`. Общий отчёт - `summary.json`.
У Marriott верхний выбранный этаж - 8, у остальных - 9; дополнительно перебираются все реальные этажи.

Фасады - настоящие рёбра контура с внешними нормалями, ближайшими к направлению на ближайший берег
и обратному. Короткий торцевой фасад не отбрасывается. Окно ставится на 0,5 м снаружи середины ребра. На каждый фасад - 141 луч с шагом 1°.
STRtree и точные пересечения дают интервалы крыш до 2 км, включая обе границы и возможный внутренний
максимум угла с кривизной. Рельеф идёт от 30 м до 40 км шагом 30/60/90 м. Кривизна Земли учитывает
рефракцию 0,13. Все тайлы, которых касаются лучи, загружаются автоматически, включая севернее 44°.

Видимость воды проверяется по упорядоченному максимуму углов предшествующих преград.
Море может быть видно **перед** горой, даже если гора образует верхний силуэт. Цвета: коричневый -
здания, зелёный - DSM, голубой - видимый интервал воды, фон - небо. Синие отметки снизу показывают
азимуты с водой, включая слишком узкие для масштаба рисунка просветы.

`sea_fraction` - доля азимутальных интервалов с любой видимой водой, а не площадь изображения,
качество вида или вероятность. Минимальный этаж ищется по этому же условию, только в пределах
этажности здания; `null` означает, что на доступных этажах в этом фасаде вода не найдена.

При построении маски координаты линий привязываются к сетке 1 см: иначе микрозазоры после
проекции могут объединить море с сушей. Проверяются контрольная точка моря и положение отеля на суше.

## Ограничения для переноса в B2.5

Copernicus - **DSM**, содержащая крыши и растительность. Основание каждого здания оценивается
20-м перцентилем 32 проб по контуру с отступом 35 м; значения DSM под зданием и в ореоле 20 м
понижаются до этой оценки перед добавлением явной высоты OSM. Это эвристика против двойного
учёта крыш, а не получение DTM. На склонах и в плотной высотной застройке она ошибается.
Высота: `height` → `building:levels × 3` → 9 м с пометкой `default` в статистике.

Номинальный результат не калиброван. В B2.5 нужны возмущения высот/оснований/положения окна,
несколько точек на фасад, проверка снимками/ответами отельера и порог практически заметного вида.
Интервалы крыш можно повторно использовать при смене этажа/высот. Сдвиг окна требует обновления
геометрии пересечений; простое переиспользование старых лучей при таком сдвиге неверно.

Проверки без установки проекта:

```sh
uv run --no-project --with numpy --with shapely --with httpx --with rasterio \
  --with pyproj --with pytest --with pytest-asyncio pytest -q backend/pipeline/spikes
uv run --no-project --with ruff ruff check backend/pipeline/spikes
uv run --no-project --with ruff ruff format --check backend/pipeline/spikes
uv run --no-project --with numpy --with shapely --with httpx --with rasterio \
  --with matplotlib --with pyproj --with mypy mypy --no-namespace-packages --follow-untyped-imports \
  backend/pipeline/spikes/horizon_{data,geometry,plot,spike}.py
```
