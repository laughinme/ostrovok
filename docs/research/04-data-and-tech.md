# 04. Данные, алгоритмы, архитектура

## 1. Регион: Большой Сочи (рекомендация)

Почему Сочи:
- **Ложится на все примеры ТЗ и эксперта**: море, закат над морем, горы (Кавказский хребет, Красная
  Поляна), «до пляжа без крутого подъёма» (город на холмах, в OSM 1 836 лестниц), шум (ж/д идёт **прямо вдоль
  пляжа**; аэропорт Адлер с глиссадой над Имеретинкой; бары на набережной), семьи, авто (пешеходные зоны,
  мало парковок), климат по месяцам («в октябре ещё купаются»), стройки (460 строящихся зданий в OSM).
- Главный курорт внутреннего туризма, а значит, ключевой рынок Островка. Тимур на Q&A назвал Сочи «хорошим
  вариантом».
- Внутри один регион с разными «мирами»: центр Сочи, Хоста/Кудепста, Адлер, Сириус/Имеретинка,
  Красная Поляна/Роза Хутор/Эсто-Садок. Это показывает, что система работает на разных типах местности.
- Риск: Сочи выберут многие. Но выигрывает глубина, а не экзотика региона.

Альтернатива — **Санкт-Петербург**: рельеф плоский, DEM почти бесполезен, но есть сильная локальная фишка —
разводка мостов («с Васильевского ночью не попадёшь в центр»), белые ночи, шум баров на Рубинштейна.
Выбирать его, только если в команде кто-то хорошо знает город.

**Скоуп для демо:** 150–400 отелей. Центр, Адлер, Сириус и Красная Поляна обязательно, остальное по времени.

### Спрашиваем у отельера (то, что нельзя посчитать)

- **Какие категории номеров выходят на какой фасад и на каких этажах.** Это ключевая связка «расчёт по
  фасаду → номер, который бронирует гость». Агент сам формулирует вопрос: «У вас 4 фасада. С юго-западного
  виден закат над морем с 3-го этажа. Какие категории номеров выходят на юго-запад?»
- Шумоизоляция и стеклопакеты на «шумной» стороне, кондиционер, плотные шторы (blackout).
- Питомцы: виды, вес, цена, где выгуливать.
- Лифт, ступени у входа (коляски, пожилые), собственный пляж, лифт к пляжу (в Сочи бывает), трансфер.
- Ранний заезд, кухня, детские кроватки.

### Принцип «когда считать, а когда спрашивать»

Считаем всё, что следует из физики и карты (вид, солнце, расстояния, уклоны, шум от внешних источников).
Спрашиваем то, что знает только отель (политики, оснащение, привязка номеров к фасадам). **Сверяем**,
когда оба источника говорят об одном (отельер: «из всех номеров вид на море» ↔ расчёт: «море видно только
с ЮЗ-фасада выше 3-го этажа») → конфликт → уточняющий вопрос → понижаем уверенность заявления отельера.

## 4. Алгоритмы (ядро)

### 4.1 Профиль горизонта и видимость (вид, закат, горы)

1. Привязываем отель к полигону здания (точка OSM → содержащий или ближайший `building`).
   Высота: `height` → иначе `building:levels × 3 м` → иначе дефолт с **низкой уверенностью**.
2. Фасады: рёбра полигона группируем по ориентации нормали (8 румбов). На каждом фасаде точки окон на высотах
   этажей (1-й, 3-й, 5-й, 7-й… или каждый).
3. Поверхность: `max(DEM, рельеф под зданием + высота здания)` на растре 2–5 м вблизи (до ~1–2 км),
   дальше DEM 30 м (до 30–50 км для гор и моря). Учитываем кривизну Земли и рефракцию: падение
   ≈ d²/(2R)·(1−k), k≈0,13.
4. Лучи по азимутам с шагом 1° в секторе обзора окна (±60–70° от нормали фасада). Вдоль луча идём шагами
   10–30 м и держим максимальный угол возвышения. Море на луче видно, если ячейка моря (маска по береговой
   линии OSM) выше текущего максимума.
5. Результат: силуэт горизонта (угол по азимуту) + разметка «море / горы / застройка / небо». Метрики:
   доля моря в FOV, мин. этаж с видом на море, видимые вершины.
6. Закат: азимут заката по датам (астрономия). Для Сочи (φ≈43,6°) он меняется от ~237° (зима) через
   270° (равноденствие) до ~303° (лето). Видимость заката = горизонт в этом азимуте не перекрыт, и под ним
   море или открытый горизонт. Береговая линия Сочи идёт на СЗ–ЮВ, море на ЮЗ, поэтому **летом солнце садится
   ближе к линии берега и может уходить за прибрежные холмы. Сезонность заката над морем надо посчитать
   и показать** — неочевидный инсайт для демо (проверить расчётом, не утверждать заранее).
7. **Уверенность через возмущения (Монте-Карло):** N=20–50 прогонов с шумом в высотах зданий (±1 этаж,
   больше для «дефолтных») и в координате точки → доля прогонов «море видно» = вероятность. Её честно и
   просто объяснить: «уверенность 0,82 = в 82% сценариев с учётом погрешности высот соседних зданий море
   видно».

Реализация: numpy, rasterio, shapely/geopandas, pyproj. GDAL `gdal_viewshed` для проверки. Тяжёлое
считаем офлайн и кладём результат в репозиторий. В рантайме — только чтение и лёгкие пересчёты (one-off по
кнопке).

### 4.2 Индекс шума (не «децибелы», а честный индекс)

- Источники с условной мощностью: trunk/primary 70–75, secondary 65, tertiary 60, residential 50, ж/д 75
  при проходе (частота поездов как множитель), бар 60 / клуб 70 ночью, если `opening_hours` после 23:00,
  стройка 65 днём.
- Уровень у фасада: энергетическая сумма по источникам, затухание 20·log10(d), −10 дБ, если луч
  «источник → фасад» перекрыт зданием, −5…−15 дБ для фасада, обращённого от источника.
- День и ночь отдельно. Шкала: тихо / умеренно / шумно + калибровка по нескольким размеченным точкам.
- Уверенность средняя (модель), в UI так и пишем. Где есть ответ отельера о шумоизоляции, учитываем его
  как отдельный факт «внутри номера».

### 4.3 Реальная пешая доступность

osmnx `network_type="walk"` по региону → высоты узлов из DEM → уклон ребра → время по Тоблеру
(`6·exp(−3.5·|slope+0.05|)` км/ч) → кратчайший путь до ближайшего входа на пляж. Атрибуты пути: время,
набор высоты, число ступеней (длина `steps`), пересечения ж/д и крупных дорог, наличие подземного перехода
или моста. Итог: «9 мин, подъём 35 м, 120 ступеней, переход через ж/д по тоннелю».

### 4.4 Достоверность и слияние источников

- Модель факта: `value`, `confidence ∈ [0,1]`, `source_type` (computed / osm_tag / open_api / hotelier /
  user_feedback / mock), `method` и версия, `evidence` (параметры, ссылки, картинки, id объектов OSM),
  `observed_at`, `valid_until` (TTL по типу источника: OSM 90 дней, климат 1 год, отельер 180 дней,
  расчёт — пока не изменились входные данные).
- Слияние: априорная надёжность источников + сложение в лог-шансах. **Конфликт**, если источники расходятся
  сильнее порога → запись в `conflicts` → правило разрешения (физика побеждает маркетинг; свежее побеждает
  старое; уточняющий вопрос отельеру) → след в истории.
- **Калибровка**: на размеченной выборке строим reliability diagram и ECE. Тезис в питч:
  «когда мы говорим 80%, мы правы примерно в 80% случаев».

### 4.5 Поиск

1. **Разбор намерения**: LLM со строгой JSON-схемой → список критериев
   `{characteristic_id, условие, важность must/nice, даты}` + список «непроверяемых пожеланий».
   Фоллбек без LLM: синонимы из реестра + эмбеддинги (локальная маленькая модель) или регулярные правила.
2. Кандидаты: SQL/PostGIS по must-критериям с порогом вероятности.
3. Скоринг: `score = Σ w_i · P(критерий_i выполнен)` + штраф за неопределённость.
   **Риск разочарования** = `Σ w_i·(1−P_i)` по must-критериям.
4. **Объяснение строится по фактам, без галлюцинаций**: шаблоны + опционально LLM-перефраз со ссылками
   на id фактов (валидация: LLM не может упомянуть то, чего нет в переданных фактах).
5. «Найди похожий»: вектор фактов отеля → косинусная близость с весами из запроса.
6. Картинка «хочу такой вид»: vision-LLM → признаки (море, горы, город, закат) → критерии.

### 4.6 Расширяемость (новая характеристика текстом)

Реестр характеристик в YAML/БД: `id`, название, описание, синонимы, тип значения, уровень (H/F/FL/D),
**рецепт** (цепочка инструментов из библиотеки: `osm_query`, `route_to`, `count_within`, `horizon`,
`sun_at`, `climate_month`, `ask_hotelier`), TTL, модель уверенности, шаблон вопроса отельеру.
Новая характеристика: описание текстом → LLM-«компилятор» собирает рецепт из инструментов → валидация схемы
→ **сухой прогон на 5 отелях** с показом результата человеку → батч по всем отелям → характеристика сразу
доступна в поиске. Пример для демо: «рядом есть хинкальная до 10 минут пешком» → `osm_query(cuisine=georgian)
+ route_to ≤ 10 мин`.

### 4.7 Диалог с отельером

- **Какие вопросы задавать:** `ценность = спрос (как часто пользователи ищут эту характеристику) ×
  неопределённость (1 − confidence) × влияние на ранжирование`. Отельеру уходят только топ-вопросы.
  Вопросы группируются в одну короткую анкету, без допроса.
- Ответ в свободной форме (текст или голос → Whisper) → LLM-разбор в поля по схеме характеристики +
  уверенность разбора → низкая уверенность ведёт к переспросу.
- **Симулятор отельера** для демо и метрик: у каждого отеля скрытый «истинный профиль». LLM-персона отвечает
  естественно, иногда расплывчато или с преувеличениями («у нас всё с видом на море»). Точность разбора
  меряем по скрытой правде.

```
└───────────────┘               ▼                  └────────────────────┘
                   ┌──────────────────────────┐
                   │ Fact Store (Postgres +   │◀── Reconciler (слияние, конфликты, TTL)
                   │ PostGIS [+ pgvector])    │◀── Hotelier agent (вопросы, разбор ответов)
                   │ facts · evidence · history│
                   │ conflicts · questions     │
                   └───────────┬──────────────┘
                               ▼
        ┌──────────────────────────────────────────────┐
        │ Hotel Knowledge API: REST (OpenAPI) + MCP    │  ← любые агенты (ChatGPT, Алиса,
        └───────┬───────────────┬──────────────┬───────┘     трек «О!дин запрос», поддержка)
                ▼               ▼              ▼
          UI путешественника  Кабинет отельера  Ops: качество, метрики, свежесть
```

Почему это «строительный блок»: Островок может взять Fact Store + API как новый источник признаков для
**своего** ранжирования, карточек, поддержки и B2B, а MCP открывает знания внешним агентам.
Событийный пересчёт: изменились OSM, здание или ответ отельера → пересчитываем зависимые факты
(граф зависимостей рецептов).

### Стек (рекомендация, финальный выбор за командой)

- Backend: **Python 3.12, FastAPI, Pydantic**, SQLAlchemy/psycopg; агентный цикл — свой минимальный или
  лёгкий фреймворк (PydanticAI / LangGraph — проверить API через Context7 перед использованием).
- Гео: numpy, rasterio, shapely 2, geopandas, pyproj, osmnx, networkx, astral/pvlib.
- БД: **PostgreSQL 16 + PostGIS** (+ pgvector при необходимости). Совпадает с их PostgreSQL-культурой.
- Frontend: **Next.js/React + MapLibre GL** (бесплатно, векторные тайлы OSM, `fill-extrusion` для 3D-зданий),
  Tailwind + shadcn/ui. Графики горизонта — SVG/D3 или Canvas.
- LLM: **любой OpenAI-совместимый endpoint** (`OPENAI_BASE_URL`, `OPENAI_API_KEY`, `LLM_MODEL`).
  Опциональный профиль Compose с локальной моделью (Ollama/vLLM, небольшая Qwen/Gemma).
  **Режим без ключа**: всё предрассчитано, поиск через фоллбек-парсер, ответы отельера заранее разобраны и
  закэшированы. Решение обязано запускаться у жюри без ключа.
- Voice (опционально): Whisper (локально или через API) для голосовых ответов отельера.

### Docker и сдача: техчек-лист

- `docker compose up --build` → `localhost:8080`, `/health` → `{"status":"ok"}`.
- Сервисы: `app` (API + статика фронта или отдельный `web`), `db` (postgis с healthcheck),
  опционально `llm` (профиль). Multi-stage, non-root, `platform: linux/amd64`, версии зафиксированы.
- Сидирование на старте: миграции + загрузка предрасчёта (GeoParquet/SQL-дамп, **десятки МБ, не сотни**).
  Скрипты пересчёта лежат рядом (`make recompute`), чтобы было видно, откуда данные.
- Время сборки ≤ 10 мин: тяжёлые гео-зависимости ставить колёсами (rasterio/shapely имеют manylinux-wheels),
  GDAL из исходников не собирать.
- Атрибуция OSM, Copernicus и Open-Meteo в UI и README.
- Проверить на чистой машине: `git clone` → `cp .env.example .env` → `docker compose up --build`.
