## 0. Быстрый режим для вопросов жюри

При подготовке нового чата один раз прочитать этот документ. В текущем чате контекст уже разобран.
Во время защиты пользователь может писать: «Жюри: вопрос», «Код: файл / функция», «Проще: вопрос».
Сначала дать готовую устную фразу из 1–3 коротких предложений. Код / файл — одной строкой, если спрашивают код.
Для уточнения — ещё один уровень подробностей. Не пересказывать расследование и не перечитывать весь проект.
Если факт отсутствует в снимке или зависит от состояния стенда, быстро обозначить это и проверить только нужный файл.
Не придумывать реализации и измерения ради скорости. Задержку ответа меньше секунды гарантировать нельзя;
цель документа — убрать повторное исследование проекта и держать типовые ответы готовыми.

## 1. Продукт и границы прототипа

Название в текущем UI — «О!кно», команда chupapis, трек «О!дин шаг до идеального отеля».
Задача: до бронирования связать желание с вариантом размещения и показать, откуда взялось обещание.
Регион — Большой Сочи: центр, Хоста, Адлер, Сириус, Красная Поляна.
В поставке 200 OSM-отелей; живой онбординг может добавлять новые, поэтому размер облачного каталога меняется.

Четыре поверхности: гость; отельер; оператор; API/MCP. Опорный путь гостя:
желание → чипы и поездка → выдача с компромиссами → окно/шум/маршрут/источники → заявка → поездка → обратная связь.

| Реализовано | Ограничение |
|---|---|
| Каталог и знания из открытых данных | Полнота OSM и высот ограничена; привязку корпуса и номера нужно проверять |
| Выбор фасада, этажа и даты окна | Модель видимости; остекление, деревья и погода не дают гарантии реального вида |
| Шум по сторонам, день/ночь | Условный индекс по источникам, не замер в номере и не санитарное заключение |
| Путь и рельеф | Неполные покрытия и входы; доступность коляски не подтверждена натурно |
| Климатические нормы | Не прогноз погоды на будущую поездку |
| Категории, тарифы, заявка, ответ | Синтетика и симулятор; не интеграция с реальным инвентарём и не платёж |
| Реальные фото Wikimedia и AI-иллюстрации | Подписи и лицензии; AI-кадры не доказывают свойства реального отеля |
| Обратная связь после поездки | Реализованный механизм, ещё не проверенный на реальных поездках |

При расхождении документов источник истины — текущий код и контракт. Старые абзацы frontend/README.md
про отсутствие фотоанализа/входа и единственную поездку устарели. Старые решения про Next.js и SSE в браузере
не являются описанием текущего фронта. В [10-defense.md](10-defense.md) исторические цифры тестов,
стоимости и метрик: произносить только с условиями и датой прогона.

## 2. Система целиком

```text
Браузер → gateway nginx :8080
              ├─ / → frontend :3000 (TanStack Start / Nitro)
              ├─ /api/ → backend :8000 (FastAPI)
              └─ /mcp, /health → backend
backend + worker → PostgreSQL 17 / PostGIS 3.5
backend + worker → Redis (события, лимиты и кэш)
init → миграции + ключи + сид; затем запускаются API/worker
pipeline → компактные геоданные → расчёты → наблюдения → сверка → факты
```

В облаке конфигурация из репозитория: фронт Vercel, API/worker Fly, PostGIS и Redis.
Адреса: https://ostrovok-okno.vercel.app/ и https://okno-api.fly.dev/health.
Это адреса из конфигурации, а не обещание постоянной доступности.

В браузере shared/api/client.ts обращается к /api/v1 того же origin.
Nitro проксирует /api/** на BACKEND_URL; в Compose gateway направляет API сразу в FastAPI.
SSR использует BACKEND_URL напрямую. Один origin упрощает cookies; это не замена проверки прав.
LLM-ключ на фронт не передаётся; конфигурация модели и запросы к провайдеру находятся на сервере.

В репозитории зафиксирована конфигурация жюри Polza.ai / openai/gpt-5.6-luna, но фактическую
модель работающего стенда нужно читать в консоли: локальный .env и облачные секреты могут отличаться.
LLM обёрнута портом LanguageModel: PydanticAI, типизированный результат, кэш с учётом модели/endpoint/
промпта/схемы, лимиты вызовов, таймаут и circuit breaker. После отказа используются правила.
Консоль показывает вызовы, токены, оценку цены и время. Оценка токенов не равна полному счёту провайдера.

Запуск поставки: cp .env.example .env → docker compose up --build → http://localhost:8080.
Тяжёлые исходные геоданные при старте скачивать не нужно: компактные данные и сид включены в поставку.
Многостадийные образы, backend/frontend работают непривилегированными пользователями;
Compose связывает запуск healthcheck-зависимостями. /health проверяет процесс, /api/ready — БД и Redis.
Пересбор данных: make data → make collect → make export-seed; это отдельная дорогая подготовка,
не действие для сцены. Секреты, VPN и глобальные настройки рабочего стенда в ходе защиты не менять.

## 3. Фронтенд: структура и ответственность

Путь исходников: frontend/src. Стек и версии берём из [package.json](../../frontend/package.json).

Query 5.101.4, Zustand 5.0.16, Tailwind 4.3.3; анимации Framer Motion и GSAP.
Не нужно заучивать минорные версии: на защите важнее назначение библиотек.

### 3.1. Путь поиска по функциям

1. pages/home/ui/home-page.tsx собирает строку через buildLandingQuery и navigate в /search?q=….
   Быстрые кнопки добавляют формулировки; семантическое выделение пожеланий делает сервер.
2. app/routes/search.tsx проверяет тип q и передаёт его SearchPage.
3. SearchPage вызывает useSearchFilters. GET /hotels и POST /intents могут выполняться независимо;
   POST /searches ждёт готового намерения. Параметры: text, chips с params/importance, trip, useProfile.
4. useSearchFilters использует Query. searchKey включает намерение, account.id, персонализацию и hotelId.
   Сервер возвращает searchId, intent, matches, рекомендации номера, perChip, tradeoff, relaxations/research.
5. Когда данные готовы или получена ошибка, SearchPage делает replace-переход в /results.
   Страница результатов использует тот же хук и QueryClient, поэтому повторно использует кэш.
6. hotelFromApi соединяет ApiHotel с ApiMatch; score × 100 округляется для UI, неизвестность хранится отдельно.
   Порядок matches уже задан сервером. matching.ts существует для локальных/вспомогательных сценариев,
   но не заменяет основной серверный ранжировщик.
7. ResultsPage показывает сначала 20 карточек, затем раскрывает следующие из полученного набора.
   Это ограничение отображения, не серверная пагинация и не виртуализация. Сервер обычно отдаёт до 30 matches.
8. Переход в /hotel/$id сохраняет sid: загрузчик читает /searches/{sid}, восстанавливая поездку,
   пожелания и рекомендацию. Один q не заменяет sid; sid не является токеном доступа.

Фильтры по запросу запоминаются в Zustand useSearchSession в памяти.
Персонализация включается только для вошедшего guest; сервер добавляет признаки профиля.
Редактирование чипов сохраняет важность и параметры, неизвестное желание можно исследовать.

### 3.2. Состояние и скорость интерфейса

| Данные | Где | Время жизни |
|---|---|---|
| Ответы API, каталог, поиск, гео | TanStack Query | 5 минут свежести, неактивные запросы 30 минут в браузере |
| Открытое окно, фасад, дата, форма | useState локального компонента | Пока живёт компонент |
| Последний запрос и фильтры | Zustand useSearchSession | Память приложения |
| Выбранные ID и критерии сравнения | Zustand persist / sessionStorage | Переживают reload в данной вкладке |
| ID избранных | Zustand persist / localStorage | Между открытиями браузера, до удаления |
| Account и access-токен | Zustand useSession | Только память |
| Refresh-токен | HttpOnly cookie сервера | По сроку сессии сервера |
| Режим local demo | okno-design-demo cookie | До 30 дней; live/demo раздельные ключи local/session storage |

QueryClient создаётся внутри getRouter, не глобальный серверный singleton.
Для SSR gcTime = Infinity, но клиент принадлежит экземпляру Router; браузерный gcTime = 30 минут.
staleTime означает срок свежести, а не фоновый опрос каждые пять минут.
Обновление после устаревания происходит при событии Query/refetch; у поиска фокусный refetch отключён.

keepPreviousData в поиске оставляет старый результат, пока идёт новый запрос.
В сравнении placeholder сохраняется только для того же набора ID, чтобы не показывать чужой состав.
Смена аккаунта отменяет активные запросы и resetQueries; выход очищает QueryClient и перезагружает страницу.
Демо меняется через cookie и загрузку страницы. persist-гидратация browser storage выполняется после монтирования.

RequestState различает загрузку, ошибку и готовность; LoadingSignal регистрирует блокирующую загрузку.
app/ui/use-loading-activity ждёт 120 мс до оверлея; Router pending имеет свой порог 120 мс.
Фоновый refetch не должен скрывать имеющиеся данные полноэкранной сценой. Минимального времени показа нет.
Сцена загрузки — векторная Земля и самолёт, не обязательно WebGL.

### 3.3. Отель, геоданные и доказательства

hotel.$id loader использует ensureQueryData с revalidateIfStale и превращает 404/422 в notFound.
Компонент также подписан на useQuery, поэтому может получить фоновое обновление.

WindowSection хранит фасад/этаж/дату и строит endpoint:
GET /hotels/{id}/window?facade=W&floor=5&date=2026-11-12.
useGeoQuery включает запрос при приближении секции к viewport (IntersectionObserver, запас 250 px).
queryKey включает hotelId и endpoint, то есть все параметры окна. AbortSignal передаётся в fetch.
Предыдущее гео можно показывать во время обновления только для того же отеля, с отметкой обновления.

Активная иллюстрация окна — WindowPanorama (SVG), данные преобразует calculatedWindowView.
Форма, масштаб и размещение объектов условны; подпись прямо говорит, что это не фото и не точные сектора.
Старые/дополнительные 3D-файлы не доказывают, что активная панорама работает на Three.js.
Three.js используется в других сценах, MapLibre — в интерактивной карте.
Модель геометрии и солнца на сервере; фронт вычисляет представление и подписи из ответа.

WhyPanel читает GET /facts/{id}: источники, дата, метод, confidence, caveats, evidence, history.
FactSourcesModal — dialog с Escape, удержанием и возвратом фокуса. Звёзды факта:
3 при confidence ≥ 0,9; 2 при ≥ 0,7; иначе 1 при положительном значении. Отдельно stale/conflict.
Это другой показатель, чем звёздность отеля и процент совпадения с запросом.

### 3.4. Агенты и обновления

POST /searches/{id}/wishes и /research возвращают runId.
useAgentRun → GET /runs/{id} раз в 1200 мс, остановка на done/failed; AgentTrace показывает реальные шаги.
useLiveResearch после завершения перечитывает поиск сразу, через 12, 30 и 50 секунд:
нужен шанс увидеть отложенный ответ демо-отельера. Таймеры и запросы очищаются при уходе/смене запуска.
Бэкенд поддерживает SSE /runs/{id}/events; этот хук фронта его не использует.

### 3.5. Заявки, поездки, вход

BookingRequest → useMutation → sessionApi POST /bookings с hotelId, roomTypeId, ratePlanId,
датами, гостями, пожеланием и при наличии searchId. Проверяет вместимость/даты в UI;
сервер тоже должен проверять запрос. После успеха invalidates tripsQuery.
GET /me/trips?limit=100 — список; GET /trips/{id} — детали, polling 2 с только при requested.
После выезда POST /trips/{id}/feedback передаёт ответы по сохранённым factId.
Всё это демо-заявки, без оплаты и реального инвентаря.

signIn/signUp/signInPersona → токены → GET /me → запись account и access-токена в память.
restoreSession делает POST /auth/refresh с X-CSRF-Token из читаемой csrf-cookie и X-Client: web.
Параллельные refresh объединены в один Promise. sessionApi обновляет токен за 30 с до истечения
или один раз после 401. При отсутствии сессии открывает диалог входа.
Refresh-cookie HttpOnly с Path=/api/v1/auth, CSRF-cookie намеренно читается JS.
Роли guest/hotelier/operator проверяются сервером; SessionGate управляет отображением и приглашением ко входу.
Тестовые аккаунты общие, не выдавать их за персональные закрытые аккаунты.

### 3.6. Голос, фото и локальное демо

Голос: SpeechRecognition/webkitSpeechRecognition, ru-RU, промежуточный текст, stop/abort,
обработка ошибок и очистка при уходе; без поддержки микрофон скрыт. Нет гарантии офлайн-распознавания браузера.
Текстовый файл .txt до 32 КиБ добавляет описание, UI ограничивает итоговый запрос 4000 символами.
Важная граница: текущие IntentRequest/SearchRequest на сервере допускают только 2000 символов;
длинный текст 2001–4000 получит 422. Для демо использовать короткий запрос; лимиты требуют согласования.

Фото: клиент проверяет MIME, размер ≤5 МиБ и ≤40 мегапикселей, через canvas уменьшает длинную сторону
до 1024 px и перекодирует в JPEG 0,82. POST /intents/photo передаёт base64 + mediaType.
Сервер повторно проверяет размер, base64 и сигнатуру. LLM формулирует желание; пользователь может поправить текст.
Фото не является доказательством свойств отеля. При отсутствии LLM — 503 и предложение написать словами.
Согласно реализации и журналу input-modes снимок не сохраняется; журнал/кэш держат SHA-256 и текст.

getApiMode читает cookie; api() в demo вызывает зарегистрированный app/demo транспорт до fetch.
Транспорт имитирует API и задержки, заявки локальные; фото в этом режиме недоступно.
Это не автономный offline/PWA: подложки карт, шрифты и другие ресурсы могут зависеть от сети.
Обычный live без ключа LLM — другой режим: запросы к настоящему серверу, геоданным и правилам.
В текущей шапке нет прежнего переключателя «Демо/Гость/Отельер»: там SessionControls.

## 4. Бэкенд: знание, расчёт, поиск

Подробная карта: [backend/ARCHITECTURE.md](../../backend/ARCHITECTURE.md).

Observation — входное утверждение: значение, источник, ссылка, время, уверенность, Scope, метод,
TTL, доказательства, оговорки, версия характеристики, runId.
Fact — текущий результат сверки: значение + confidence + область + статус ok/stale/conflict.
Scope: фасады N/NE/E/SE/S/SW/W/NW, включительные этажи, месяцы; категории связываются с фасадами/этажами.
Хранимое знание обычно месячное, окно и солнце API считает на конкретный день.

Запись: KnowledgeStore.record → advisory lock пары отель/характеристика → observations → reconcile
→ facts / fact_versions / conflicts в транзакции UoW. Версии существенных изменений сохраняются.
Сверщик — детерминированный код. Для вероятностей — сетка фасад × этаж × месяц и взвешенные log-odds.
authority=physics предпочитает физический расчёт, hotelier — правила проживания отеля; конфликт не прячется.
confidence у false относится к отрицательному утверждению: false с 0,95 даёт P(да)=0,05.
Затухание действует при сверке после 80% TTL; чтение не пересчитывает confidence само.

| Расчёт | Как | Чего не утверждать |
|---|---|---|
| Вид | Лучи/горизонт по OSM-зданиям и DSM, море/горы, высота окна | Фотореалистичность и точность до конкретного остекления |
| Устойчивость вида | Монте-Карло с возмущениями высот/окна/этажа, обычно 16 сценариев | Измеренную accuracy на реальных окнах |
| Закат | Astral + горизонт и геометрия на дату | Облачность и прогноз ясного неба |
| Шум | Источники OSM, условные мощности, расстояние, сторона и экранирование | LAeq в номере или натурную шумовую карту |
| Путь | OSM-граф, SciPy/Dijkstra, Тоблер и уклоны, отдельно обратно | Полную доступность для коляски при неизвестных покрытиях |
| Климат | Многолетние нормы Open-Meteo | Погоду конкретной даты |

Куратор составляет структурированный рецепт из закрытых типов: view, sun_event, noise, walk_to,
poi_nearby, area_stat, climate, ask_hotelier, derived. Pydantic проверяет схему, затем пробный прогон.
Новая характеристика в рамках методов — данные; новый вычислительный метод — код и тесты.
LLM не генерирует произвольную выполняемую программу. Инструменты Куратора — словарь и статистика тегов OSM.
Исследователь исполняет рецепты, Связной спрашивает отель, Наблюдатель запускает пересчёт при изменении мира.
Постройка/откат дома оператором — управляемое событие, автоматической подписки на обновления OSM нет.

Поиск перебирает варианты номера/фасада/этажей по сохранённым фактам.
Важность must/important/nice имеет веса 3/2/1. Неизвестное — внутренний приор 0,5, но вердикт unknown.
score = средневзвешенное P × произведение min(1, 0.5+P) для must.
risk = 1 − произведение P важных и обязательных пожеланий; эвристика с допущением независимости.
Непокрытые ячейки отдельно не штрафуются: усредняются покрытые. Это известное ограничение модели.
Бюджет/вместимость/регион фильтрует сервер. Полный каталог кандидатов пока читается целиком.
MCP: пять read-only инструментов поверх тех же сервисов; его текстовый поиск сейчас использует правила,
не создаёт сохранённый поиск и исследовательские задачи.

Бронь сохраняет снимок обещаний и областей. После подтверждённой поездки и выезда ответы гостя
по булевым фактам обновляют оценку в области обещания: (10p + yes)/(10 + yes + no).
Один отзыв не меняет весь отель; повторные ответы ограничены. Это не промышленный антифрод.
